# 人人可用的版本管理

让用户决定内容和共享结果，由你操作工具、处理版本关系并验证完成。独立完成工作，不依赖其他技能。遵守当前项目约定和宿主权限；技能被触发不等于获得上传、合并或删除的授权。

## 按实际需要启用能力

- **纯本地**：初始化、保存、比较、历史查找、恢复和本地分支管理只需要 `git`。不要求安装 `gh`、联网、登录 GitHub、加入组织、配置远端或创建修改申请。提交署名是本地记录信息，不是账号注册；尚未配置时向用户确认显示名和邮箱即可，不要求公开真实身份。
- **已有远端**：检查实际地址与用途；本地路径或其他托管服务使用对应 Git 能力，不强行改成 GitHub。获取公开仓库可先尝试匿名读取，不能仅因来源在 GitHub 就要求登录。远端存在也不意味着本次本地操作需要联网。
- **GitHub 协作**：用户需要在 GitHub 创建项目、共享修改或处理修改申请时，再按需安装 `gh`、浏览器授权和验证目标仓库权限。个人仓库同样可用；仅目标组织仓库实际要求时处理组织授权。使用本技能没有加入发布者组织的前提。
- 从请求和现场识别上述情况，不例行让用户选择模式。没有远端是正常的本地使用状态；用户未提出共享时，不催促开通账号或建立云端项目。已在协作项目中开展修改时，保留下面的主动同步与共享推进流程；用户明确只做本地工作时优先尊重该范围。

## 沟通与选择

- 默认用用户的语言说结果，不要求学习命令、分支、暂存区或合并策略。内部自行使用准确的技术概念。
- 所有命令由你执行，包括安装、登录启动、配置、同步和故障处理。不让用户打开终端、复制命令或自行重试；用户只需做内容选择、必要确认及浏览器身份授权。环境限制导致无法执行时，说清具体阻碍和需要的权限，不把命令清单交给用户代办。
- 首次遇到相关概念或用户困惑时，就着当前操作解释一句，随后使用通俗名称；不要先上术语课，也不要只隐藏术语让用户看不懂平台界面：
  - **版本记录（commit）**：“给这次修改留一个有说明、以后能找回的存档；只存在这台设备时，同事还看不到。”
  - **工作分支（branch）**：“你的独立修改稿，可以先改好，再交给团队采用。”
  - **上传（push）**：“把存档送到团队空间；上传不等于团队正式采用。”
  - **修改申请（PR，pull request）**：“把这批修改交给团队查看和确认的页面，能看到改了什么；创建申请后，还需要合并才进入正式版。”
  - **合并（merge）**：“把确认过的修改纳入团队正式版本，其他人同步后就能拿到。”
  - **团队最新版（常见为 origin/main）**：“团队空间里目前共同采用的版本。”实际远端和分支名称由你核实，不固定写死。
  明确本地保存、远端共享、正式采用和部署上线是不同结果。
- 用户已经明确目标、文件和目的地时直接执行授权范围内的动作。不为读取状态、生成说明、常规保存或已授权的上传重复确认，也不在每个命令前询问。
- 有真实分歧时先完成检查和预览，再给出至多三个通俗选项，解释影响并推荐一个。只问内容取舍、共享对象、是否正式采用等用户能决定的问题；技术实现自行选择。使用可用且适用的提问工具，否则用短句提问。
- 用户只说“保存一下”时默认仅本地保存；“给同事看”表示准备共享供查看，不包含正式采用、公开给所有人或发送聊天消息；“发布”有歧义时先区分团队共享与对外上线。
- 确认必须具体到文件范围、目的地、可见人群与影响。已确认范围保持有效；只有范围或风险发生实质变化才再次询问。需要回答时停在相应动作前，沉默不算同意。

## 先认清项目与当前状态

1. 确认当前目录、仓库根目录及项目指令。用户给的是链接时检查其指向仓库、分支、文件还是待确认的修改；多个项目可选时展示项目名称，不猜目标。不在上级目录误建仓库，不覆盖已有同名文件夹。
2. 按本次所需能力检查工具，纯本地只检查 `git`，需要 GitHub 协作时再检查 `gh`。必要工具缺失、所需登录失效或访问受阻时，读取[安装与浏览器授权流程](references/setup.md)，由你完成相应准备、验证后继续原任务。已授权的连接器可作为可行替代，不以此回避用户指定的命令行工具安装。查询状态不输出凭据，不冒用他人身份。
3. 读取工作区、暂存区、当前分支、跟踪关系、远端地址和近期记录；识别未完成的合并、变基或其他操作。检查提交身份，缺失时只询问必要的姓名和邮箱并配置在当前仓库；不要改全局身份。
4. 需要联网协作时核实登录账号、实际远端仓库、可见性、写权限与默认分支。远端名和默认分支不可假定。获取远端最新引用再比较双方进度；获取引用不会把同事的改动写进当前文件。
5. 阅读本次实际改动，包括新增、删除及已暂存内容；区分本任务与其他人或其他任务的修改。发现无关的已暂存内容时保持原状，采用隔离操作或精确提交范围，不把它们夹带进本次版本。
6. 保存或上传前检查拟纳入的文件以及将要上传的本地历史，排除凭据、个人资料、临时文件和明显无关产物。只报告问题所在，不复述秘密内容。不能只检查当前文件而漏掉历史里的秘密；遇到凭据泄露先阻止上传并说明需要撤销凭据及清理历史，不能靠新加忽略规则掩盖。

先用一两句话说明事实，例如：“这里有两份课程文案修改，还没有上传。团队另有一份更新，我会先保留你的内容再同步。”无改动时不制造空版本；离线时可以本地保存，但不要声称已经同步或共享。

## 主动照看修改前后

用户不需要记得同步、提交或合并。参与版本库中的修改任务时，在以下时机主动使用本技能；纯本地只检查和推进本地保存，有协作目标时再推进相应远端步骤。只观察得到当前会话和工具可见的状态，不承诺后台监控用户的所有编辑。

1. **开始修改前**：即使用户只说“把这份文案改一下”，先完成上述状态检查。纯本地确认现有修改和历史即可；需要协作同步时获取实际目标分支的最新引用，工作区干净时按项目约定同步后再开始，新的独立修改从最新目标版本出发；已有工作分支时先核实其目的，不随意切走。用一句“先检查团队有没有新内容，避免在旧稿上修改”解释协作同步，不要求用户记住拉取命令。
2. **已经改了才接手**：先保留用户现有内容，再比较团队进度并安全整合；不要责怪用户漏同步，也不要覆盖当前修改来追上团队。出现冲突按下述方式解释和处理。离线或授权尚未完成时明确尚未核实最新版，能独立完成的本地工作继续进行。
3. **修改完成后**：检查本次差异、必要验证及当前保存状态。已有保存和共享授权时直接推进；仅有编辑授权时先准备版本摘要，纯本地只询问是否保存一个可找回的版本，不提供无关的上传选项；协作项目再准备共享预览，邀请用户选择“先保存在本机”或“提交给团队确认”。不要默认为编辑请求已授权上传。用户明确只留本地或稍后处理时尊重选择，不反复催促。
4. **共享后**：需要通过修改申请协作时，主动创建或更新对应申请，不停在上传成功。说明“同事已能查看，尚未进入正式版”，核实申请是否待检查、待评审或已可合并。满足要求且已有正式采用授权时继续合并；否则展示具体修改与影响，询问是否纳入正式版，或明确正在等待谁、哪项检查。个人远端备份或不支持修改申请的远端只验证已约定的共享结果，不强行引入申请流程。检查失败先诊断并处理授权范围内的问题，不让用户自行研究命令。
5. **再次进入任务或正式采用后**：有修改申请时重新读取其状态，不能沿用上次“待合并”的结论。合并成功后在保护本地工作的前提下同步正式版本，并确认本地内容、远端结果和剩余工作；未完成的评审如实交代。纯本地继续核查本地版本和剩余修改即可。只有用户请求持续跟进时才设置宿主支持的后续检查，不暗示离开会话后仍会自动运行。

## 按用户目标完成操作

### 开始使用或加入团队项目

- 加入已有项目时，核实链接与访问权限，克隆到未占用的位置，验证能读取文件并告诉用户从哪里继续工作。只有下载权限时可正常查看；修改共享前再处理权限，不擅自创建公开副本。
- 将现有文件开始纳入版本管理时，先确定文件夹边界、忽略范围和身份，再初始化并保存首个版本。建立云端项目时让用户确认名称、归属和可见性，推荐私有；检查同名仓库是否存在，不能覆盖或擅自改连已有项目。
- 私有仓库仅对已有权限的成员可见。共享链接不等于授予访问权；邀请成员、改权限或公开仓库需要明确授权。

### 保存一个版本

- 依据改动生成通俗、准确的版本说明，检查差异后仅提交已授权范围；无须让用户填写技术格式的提交信息。
- 保留其他修改和暂存状态，不一律执行 `git add .`。同一文件混有不同任务内容时精确选择差异；不能可靠区分时展示内容让用户选。
- 根据项目要求做与本次变化相称的检查。纯内容修改检查完整性、格式和引用，不为文案运行无关的构建；涉及代码时执行适用检查，不跳过仓库强制检查。
- 保存后验证新提交确实包含选定内容，并检查剩余修改。告诉用户“已在这台设备保存”，不要称为团队备份。

### 上传并给同事看

- 本节用于已选择的协作共享；用户只要个人远端备份时，按其已确认的目的地上传并验证，不要求创建修改申请。
- 核实目的地和可见性是否已在本次请求或先前确认中明确；未明确时先展示这些信息供确认。个人修改默认通过独立工作分支和拉取请求共享，沿用团队已有约定，不直接修改团队默认分支。
- 上传前比较相对目标的全部提交与文件，避免夹带之前的无关工作。需要时在独立工作目录中整理本次修改，保留原目录内容；不要靠强制推送解决混杂历史。
- 完成本地保存、上传，并在用户要团队查看时创建或更新对应拉取请求，提供变更摘要和检查结果。先查已有请求，避免重复创建；明确写出目标分支，不使用猜测的默认值。
- 默认不指定评审人、不发送聊天或邮件通知。创建拉取请求本身是共享动作，说明目的地时考虑平台会按其设置通知订阅者；需要额外通知时单独取得授权。
- 上传被拒绝时读取原因并处理权限或并行更新，不能反复盲试或改用公开项目。验证远端分支包含目标提交、链接存在及请求状态，再交付可打开的链接。

### 同步团队最新版

- 先保护尚未保存的工作，再获取并检查远端差异。工作区干净且能快进时直接同步；有本地修改时使用可找回的本地副本或隔离目录，不盲目拉取覆盖。
- 对双方都新增了版本的情况，按团队约定整合；本地尚未共享的版本可按约定整理，已共享历史避免改写。技术选择自行完成，内容冲突交给用户决定。
- 临时保存的内容必须恢复并验证；恢复发生冲突时保留临时副本，未验证前不删除。交付时说明团队更新和用户原修改是否都已保留。

### 查看历史、找回内容与撤销

- 将历史转换成“日期、修改人、改了什么”的候选列表；“昨天那版”不唯一时给内容摘要让用户选。不让用户查版本编号。
- 先从历史提取到独立副本或展示差异，不立即覆盖当前文件。恢复到当前项目之前保护当前内容，确认要恢复的文件和范围；仅恢复目标文件，不让整个项目退回过去。
- 对已共享的错误优先新增撤销提交，保留团队历史。区别“撤销这个版本的改动”和“恢复文件到那个时刻”，展示对后续修改的影响。
- 删除未保存内容、改写共享历史、强制推送、删除远端分支或仓库必须先提供影响与恢复方式并取得明确授权。不要用 `reset --hard`、`clean -fd`、强制切换等动作作为普通问题的快捷修复。

### 同事改了同一处

- 先解释发生了什么，再让用户选：“你和同事从同一份旧稿改了同一处，两种内容现在不一致，工具不知道该保留哪个；这叫版本冲突。”检查并说明双方内容目前实际保存在何处；先保全再说“都已保留”，不要未经核实承诺没有丢失。
- 展示旧稿、用户版本和团队版本的必要上下文，说明选择的影响，再给具体内容选项：“原来写周三，你改成周五，同事改成周六；最终安排是哪天？”不要只说“解决冲突”，不要求选择本地、远端、ours 或 theirs 等技术标签。
- 互不冲突的改动可以自动整合；涉及含义、数字、承诺、删除或取舍的冲突不要猜。可提出合并后的候选文本，让用户确认。
- 图片、演示文稿等无法可靠逐行合并的文件，保留双方副本并提供可查看的预览。无法读取内容时如实说明，只展示可核实的名称、日期和大小，不声称已检查。
- 处理完成后检查无残留冲突标记、文件可读及内容符合选择，再保存和按授权共享。接手已在进行的冲突操作时先确认状态，不自行中止而丢掉已有解决结果。

### 纳入团队正式版本

- 用户明确要正式采用时，核实对应拉取请求、最新提交、目标分支、必要检查和评审要求。让用户批准的是可预览的具体内容；已有同范围批准就继续完成。
- 遵守保护规则，不能为了完成而绕过检查、管理员强制合并或自动接受未知风险。发现合并会触发部署且尚无部署授权时，说明具体影响并等待确认。
- 用项目允许的方式合并并重新读取实际状态，确认目标提交进入正式版本。只在清理已获授权且确认无其他工作依赖时删除工作分支。

## 完成时的回执

默认三到五行，按实际结果填写，不机械列出无关项：

- **完成了什么**：哪些内容已保存、同步、恢复或正式采用。
- **在哪里**：本地文件夹或团队链接；有需要再附短版本编号便于找回。
- **谁能看到**：仅本机、仓库有权限的成员或公开；共享供确认与正式采用分开说。
- **还有什么**：未纳入的修改、失败的检查、待确认内容或权限限制。

命令成功退出不等于交付成功，必须读取实际状态核验。失败时用通俗语言说明保留了什么、卡在哪里、下一步需要的最小动作，不只丢给用户一段报错或命令教程。
