# 安装与浏览器授权

在工具缺失、登录失效、身份不符或仓库访问受阻时读取。命令和技术判断全部由智能体完成；不要把下面的操作步骤转发成让用户执行的教程。

先判定本次操作是否需要 GitHub。纯本地只补齐 `git`，到安装验证完成就返回原任务，完全跳过 `gh` 安装与登录。其他服务或本地路径远端使用已有 Git 访问方式。公开仓库的只读获取先尝试匿名访问；只为确实需要的 GitHub 操作准备授权。

## 安装工具

1. 检测操作系统、架构、本次需要的 `git` 或 `gh`、包管理器及可写安装位置。先区分确实未安装和当前会话找不到程序，避免重复安装或改坏现有环境。
2. 按 [GitHub CLI 官方安装说明](https://github.com/cli/cli#installation)选择匹配平台的方式，由你执行。优先复用已有包管理器；没有时可使用官方发布且适配当前平台的安装包或二进制，下载后验证官方提供的校验信息。不要为了一个工具擅自安装整套新环境，也不要关闭签名验证。缺少 `git` 时同样由你按平台官方方式补齐。
3. 在宿主允许的范围完成安装；需要系统权限时优先考虑官方支持的用户目录安装方式，不能绕过宿主限制。确实需要管理员批准时，让用户批准系统提示或请管理员授权，不要求用户执行命令、透露管理员密码。
4. 执行版本检查，并确认当前会话可调用。安装失败由你读错误、处理路径或依赖后再验证；不能以“请安装后回来”结束已可代办的步骤。

## 由你发起登录，用户只在浏览器授权

1. 从实际仓库地址确定主机，不将企业实例替换成公共网站。执行 `gh auth status --hostname <host>` 检查目标主机状态，避免展示令牌。已有可用账号时核实身份和仓库权限；若环境变量提供了身份，检查其是否影响当前账号选择，但不打印变量值。不擅自退出或切换用户已有账号。
2. 没有有效登录时，先查看当前版本的 `gh auth login --help`，由你在可持续交互的终端会话启动 `gh auth login --hostname <host> --web`。新配置优先使用 HTTPS，可按当前帮助添加 `--git-protocol https`，减少生成密钥的步骤；已有协议和凭据配置先检查，避免影响其他项目。终端里的技术选项、继续提示由你处理。
3. 打开本次登录流程产生的官方授权页面；支持时可用 `--clipboard` 复制一次性设备验证码，让用户在页面粘贴并授权。页面未自动打开时由你打开，远程或无浏览器环境则提供本次流程实际返回的授权链接和设备验证码。只让用户在浏览器完成登录、多因素验证、账号选择和组织批准，不要求返回密码、令牌、恢复码或授权后的网址。
4. 清楚告知：“我已准备好登录，请在打开的官方页面确认账号并授权，完成后我会继续。”保留登录进程，使用宿主支持的交互或有界等待检查结果，不结束进程后让用户重跑。验证码过期时由你重新发起，授权仍必须由用户完成；不能替用户点击批准或把没有回答当作授权。
5. 浏览器完成后由你再次执行身份状态检查，并用只读仓库查询验证实际访问权；浏览器显示登录成功不代表命令行已登录，也不代表有团队写权限。仅在需要且影响范围明确时，按 `gh auth setup-git --help` 配置目标主机的 Git 凭据连接，不覆盖无关凭据配置。不要读取或回显令牌来手工拼接远端地址，不使用 `--insecure-storage` 作为快捷修复。
6. 若账号正确但组织单点登录或仓库权限尚缺，定位到官方授权页面或具体需要的访问申请，让用户完成浏览器确认；不擅自扩大权限、创建副本或更改仓库可见性。无安全凭据存储方式时说明环境阻碍，不能静默退化为明文存储。
7. 验证后立即继续原来的下载、同步、共享或合并任务；不要只汇报“登录成功”就结束。提交署名与登录账号是不同配置，仍需按技能正文核实当前仓库的姓名和邮箱。

命令选项以本机帮助和[官方登录文档](https://cli.github.com/manual/gh_auth_login)为准。用户已经登录网页但工具未登录、授权过期、安装后路径未刷新等常见问题都由你诊断；用户不承担终端排错。
